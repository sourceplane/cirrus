# saas-bootstrap-engine — Risks and open questions

Status: Decisions taken, with their reasons, and the questions still open.

## Decisions taken

| Decision | Why |
|---|---|
| **The Blueprint is the only execution artifact; `kind: Workflow` leaves the bootstrap path.** | The eight phase workflows express one contract eight times and share a 20-line preamble 59 times. A workflow step has no context, so every phase re-derives the baseline checkout by hand. A Blueprint phase has both context and a barrier already. |
| **orun verbs become typed actions (`uses:` + `with:`), not `run: ["orun", …]` argv.** | Five differences, all real: a bad parameter is a validation error naming the line instead of an exit code mid-bootstrap; no binary need be on `PATH`; hook outputs become addressable (argv hooks have none — `hookRunner` sends stdout to stderr and discards it); failures are typed; and a closed action set is an actual audit boundary for steps that already run *outside* the template sandbox. |
| **`run:` survives, for ecosystem escapes only.** | orun's invariant 8 — its core names no ecosystem. An *action* is orun's own surface; *argv* is how a baseline reaches `node`. Today that is the rebrand and the docs renderer. |
| **Phase state is derived; a stored file is a cache and must be safe to delete.** | `.orun/*` is gitignored here and in every product, so the archived per-phase provenance has never survived a container — and the paced bootstrap works anyway. Deriving is what makes "a different session, months later, a fresh container" possible at all. A ledger would quietly become the source of truth and break it. |
| **Inputs on resume are a conflict, not an override.** | `InputsHash` already exists in provenance. A product half-branded *Acme* and half *Acme Cloud* is a silent, expensive failure; re-inputting is `upgrade`'s operation, not resume's. |
| **The agent is retired from the build path.** | It is the execution host *and* the narrator, and it is bad at the second job by construction: the brief tells it to strip the `ACTION REQUIRED:`/`FAILED:` prefixes, so orun-cloud's `build-model.ts` can draw only four of six row states and says so in its own header. Determinism is the fix it already names. |
| **Narration is pre-authored prose in the YAML, templated over state, and may never set state.** | Prose in a file is reviewed in a PR, diffed like code and identical every run. A model's paraphrase is none of those, and is untestable — Tier 3 can assert a declared sequence and cannot assert a generated one. |
| **`split-phases.py` is deleted rather than kept for compatibility.** | It exists only because one blueprint had to become eight files for eight workflows. Its ugliest behaviour — pruning cross-phase `dependsOn` edges because an undeclared dependency is a hard validation error — is precisely what orun's phase barrier enforces natively. Keeping it would keep the fake alongside the real thing. |
| **The CI ladder puts the leak gate in Tier 1, not Tier 3.** | The `ai-context` module ships this repo's `fork-from-baseline.md`, `decisions.md` and `open-risks.md` into every product, which `BOOTSTRAP.md` explicitly promises does not happen — and after rebrand they become false statements about the customer's product. That is a one-minute static check, not an hour-long one. |
| **Tier 3 is mandatory before a `baseline-vN` tag, not merely nightly.** | The tag is what customers build from. A nightly that is red for three days blocks nothing today; a required check on the tag workflow is the only gate that sits between a regression and a customer. |

## Open questions

| # | Question | Leaning |
|---|---|---|
| 1 | **Who executes the hour?** Retiring the agent leaves the execution host open: a platform-hosted runner (same sandbox, minus the model), the product repo's own CI, or the operator's machine. | **The platform-hosted runner.** The grant, the token refresh, the sandbox and the lifecycle already exist and work — this removes the model from a box that already runs `orun`. The product repo's CI is circular for first boot (phase 01 *creates* the repo and its CI), so it is a later optimisation for resume only. `--local` remains the CI and power-user path. Owned by orun-cloud **BE-K4**. |
| 2 | ~~**Does orun's `cycleBreak` actually replace `cycle-break.mjs`?**~~ | **ANSWERED in BE1: no, and the premise was wrong.** The question assumed `repo-blueprint.yaml` carried a `cycleBreak:` declaration to compare against. It never has — the file has no such key, and the worker modules' `dependsOn`/`wiring` edges are acyclic, so orun's DAG has never seen this cycle. It lives in the wrangler config a *deploy* reads, not in the placement order. `cycle-break.mjs` is therefore not an ordering workaround orun could absorb; it is a deploy-time edit to a file, and it survives BE4 as a `run:` hook. |
| 3 | ~~**How much of `ai/context/` should a product carry?**~~ | **ANSWERED in BE5a: exactly two files.** `deployment.md` and `operations.md` are the product's — one regenerated from probed facts, one its operating guide. `current.md`, `decisions.md`, `open-risks.md` and `fork-from-baseline.md` are this repository's own state and now ship to nobody. There is no file list on a copy module, so it is one module per file, and that is the feature rather than the workaround: a new file in `ai/context/` cannot ship without somebody writing a module and arguing for it in a diff. |
| 4 | **Do the per-phase remote-reference URLs need preserving?** `orun workflow run github:…//flows/phases/03/workflow.yaml` is documented in `BOOTSTRAP.md` and every phase README. | Replace with `--phase 03-infrastructure` on the one pinned blueprint, and say so in the release notes of the tag that carries BE4. One pinned artifact is the better property; the churn is documentation, not capability. |
| 5 | **Is the closed action set a plugin system in disguise?** Every new capability needs an orun release. | Accept the cost while the set is small (eight actions). Treat "baselines keep needing new actions" as the signal to stop and reconsider, not as a reason to add an extension mechanism up front. |
| 6 | **What replaces the agent's one genuine strength — improvising around a novel failure?** | `narrate.failed` per phase, the full detail log, and an **"Ask about this failure"** affordance in the console that opens a session scoped to *reading* the log: advisory, no grant, no write access. The agent becomes a debugging affordance rather than the execution path. Owned by orun-cloud **BE-K2**. |

### Opened by BE1

| # | Question | Leaning |
|---|---|---|
| 7 | **A hook-only phase derives as `done` from placement alone.** `derivePhase` returns `PhaseDone` for a phase that places no files — "there is nothing that could be missing" — which is right for a consume-only phase and wrong for `04-workers-restore` and `08-docs`, whose whole content is hooks. `--resume` will skip them, and `requires.phases: [08-docs]` would always pass. | The derivation rule says phase state is *derived*, and for these two the tree is silent: the truth is in the task plane (is the landing folded?) and the probe (does the deployment answer?). orun's `Derive` should consult a phase's own `requires.probe`, or a declared `doneWhen`, before calling a hook-only phase done. Tracked as orun **BE-O10**, which shipped `PhaseUnknown` and made the gate fail closed. ~~which is why nothing declares one on them~~ — **that clause was false about the file.** BE1 shipped `05-edge` requiring `04-workers-restore`, so the gate could never pass and that phase refused for the whole of a real bootstrap. It surfaced only once orun BE-O12 let the phases before it through: `✕ phase "05-edge" requires 04-workers-restore (unknown)`. Fixed in BE5b — `05-edge` now requires `04-workers`, which the tree can answer for, and `phases.test.sh` gates the class so no phase can gate on a hook-only one again. The `doneWhen` half remains open. |
| 8 | **`requires.probe` makes an offline placement impossible.** Tier 1 is *dry instantiation, no network*, but a probe runs before placement unconditionally — `orun new --phase 03-infrastructure` against an empty directory now fails at `orun.doctor/check@v1` with "no workspace", which is correct behaviour and fatal to the tier. | The engine already has the seam: `Options.Actions` takes a substitute runner, which is exactly what Tier 2 is specified to use. What is missing is a way to reach it from the CLI. Decide in BE5 whether that is a flag (`--actions=none`) or whether Tier 1 simply asserts the *plan* (`--status`, which derives without probing) and leaves execution to Tier 2. BE1 verified its own placement equivalence through `--status --json`, which needs neither. |

### Opened by BE5a

| # | Question | Leaning |
|---|---|---|
| 9 | **A whole-blueprint `orun new` cannot run.** Found on Tier 1's first execution: every phase's `requires` is checked BEFORE the first byte is written, so `02-foundation` asks whether `01-scaffold` is on disk during the run that is about to write it, and always answers no. A bootstrap is unaffected — it runs phase by phase, and the tree accumulates — but a dry instantiation, which is the whole of Tier 1, cannot place the tree at all. | `requires.phases` should be satisfied by a phase placed EARLIER IN THE SAME RUN as well as by one already derived on disk. The check is asking "will this be there when my hooks run", and in a full run the answer is yes. Tracked as orun **BE-O11**, with question 8's other half: a run that does not execute hooks arguably should not probe either, since `requires.probe` gates the work and not the bytes. |

## Risks

| Risk | Mitigation |
|---|---|
| **The cluster stalls half-migrated**, with `flows/` still present and the blueprint carrying phases — two ways to run a bootstrap, and drift between them. | BE4's gate is explicit and its dependencies are named. If BE-O5/BE-O8 slip, BE1–BE3 still land value (one blueprint, narration authored, inputs validated) and `flows/` keeps working unchanged, because the phases it reads and the phases orun reads are the same declaration. |
| **Tier 3 costs real money and leaks real resources** if teardown is skipped or a run is cancelled mid-flight. | Teardown is an `always()` step, not a final step; scratch names carry the run id so an orphan is identifiable; a weekly sweep job retires anything matching `scratch-*` older than 24h. Budgeted at ~30 runs/month with `concurrency: 1`. |
| **The narration contract rots into decoration** — prose that no longer matches what the engine does. | Rule 3 of `design.md` §4: it is conformance-tested like `secrets` and `programme` already are, against the event schema rather than against another copy of itself. Tier 3 asserts the emitted sequence against the declared one. |
| **Retiring the agent removes the only thing that could ask a follow-up question** mid-build. | Every input is collected and validated *before* Build, which is why BE3 is a prerequisite rather than a nicety. An input the console cannot collect is a baseline-design error surfaced by the Tier 0 pattern check, not a runtime prompt. |
| **This repository's CI cannot run `orun validate`** if the binary's floor moves faster than the pinned action version. | The floor is already pinned (`v2.52.6` in the product lane); BE5 pins the same version in the contract job and Tier 4's reciprocal test in orun tells the binary which baselines a change breaks. |

### Opened by BE4

| # | Question | Leaning |
|---|---|---|
| 13 | **`subdomain` has no resolver.** `blueprint.yaml` declares it with a `probe`, and BE-K3 established that `probe` is inert end to end — nothing in orun-cloud resolves one, so a baseline that declares it silently drops the input. BE4's rename makes the blueprint read the same key the console shows, which closes the *translation* gap but not this one: the workers.dev subdomain is a fact of the operator's Cloudflare account, and it is still typed by hand into a field whose help text is a guess. | **A typed `orun.cloudflare/subdomain@v1` action plus a probe resolver at the bootstrap door**, so the console fills the field from the connected account before the operator sees the form. It is one action and one call site; the alternative is leaving a required-shaped input that nothing can verify until a worker deploys under the wrong name. Not BE4's — BE4's job was to make the key the same word on both sides. |
| 14 | **The early credential write-probe is gone.** The umbrella ran `create-secrets.sh` right after the scaffold, at about minute two, precisely so a builder/viewer key died THERE with the re-mint-as-admin hint rather than thirty minutes later at phase 03. The blueprint has no equivalent: the first credential WRITE is now `03-infrastructure`'s `orun.integrations/reconcile@v1`, so a sub-admin key gets through two phases and a repo creation first. Nothing is broken — the failure is still exact and still actionable — but it costs an operator twenty-odd minutes and a half-built product. Documented as a known cost in `docs/phases/README.md` rather than left to be discovered. | **`01-scaffold` gains a `requires.probe` that asserts the credential can write**, which is the shape the rest of the document already uses for preconditions — `03-infrastructure` waits on consent this way, `04-workers` on published keys. The honest version is not a fourth reconcile (it would mint real secrets a phase early); it is a `secrets/canWrite`-style check, or `orun.integrations/reconcile@v1` against an empty `keys:` list if the action's read path alone is enough to surface the role. Needs one orun change, so it is BE-O work, not BE4's. |

### Opened by BE6 (found while sizing it, before writing any of it)

| # | Question | Leaning |
|---|---|---|
| 15 | **BE6's run command is `orun baseline new`, which does not exist in any release.** The plan and `design.md` §6 both spell tier 3's invocation `orun baseline new cirrus@<sha> --org … --local --resume --progress json`. That verb is orun **BE-O7b** (`baseline new\|register\|publish`), unstarted. What a bootstrap runs today is a pinned clone plus `orun new --blueprint repo-blueprint.yaml --run-hooks --resume`, which BE4 made the documented form everywhere else. | **Write tier 3 against what works today.** The lane is a CI workflow, and the eventual `baseline new` is one line of it — a fetch-and-invoke wrapper over exactly this. Blocking the epic's only end-to-end gate on an unstarted orun milestone trades a gate that exists for a command that reads better, and BE6's whole point is that this run has never happened. Recorded rather than silently substituted, because the design says otherwise and a reader deserves to know which is current. |
| 16 | **Tier 3 needs two credentials this repository deliberately does not hold, and saying so is a decision, not an implementation detail.** `design.md` §6 costs tier 3 at *"an admin-role workspace key and a Cloudflare token with D1 Write"*. cirrus's CI holds exactly one secret today — `GITHUB_TOKEN` — and that is stated as an architecture invariant in `BOOTSTRAP.md`: *"CI holds one credential: `GITHUB_TOKEN`. Provider credentials are brokered per run from workspace integrations … **no long-lived provider tokens anywhere**."* Tier 3 as designed puts a long-lived Cloudflare account token with D1 Write into GitHub Actions secrets, which is the thing that sentence promises does not exist here. The blast radius is one throwaway tenant per run, but the token is not scoped to it — it is the account token the provision flow connects the integration from. | **Not ours to decide unilaterally, and it is the gate on the rest of BE6.** Three shapes, in order of preference: (a) a **dedicated Cloudflare account** for rehearsals, whose token can do nothing to production, with its token and an admin-role key for a rehearsal-only workspace stored as repository secrets — the invariant's sentence then needs narrowing to the deploy path it was written about, in the same change; (b) `workflow_dispatch` only, with the operator supplying the token at dispatch, which keeps the invariant exactly but means the *tag gate cannot be automatic* and BE6's done-when is unreachable; (c) run tier 3 from orun-cloud, which already brokers provider credentials — but then the baseline's own release gate lives in another repository, which is the coupling this epic spent BE1–BE4 removing. Until this is answered, BE6 ships nothing: a tag gate that no-ops is not a gate, and a workflow committed against secrets nobody has provisioned is a lane that is red or skipped forever. |
